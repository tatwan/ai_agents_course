[W5D2 s4] AWS Strands: key features | What stands out | Tools | a typed function plus a docstring under @tool, schema derived for you | MCP | MCPClient passed into Agent(tools=[fs]), managed lifecycle handles it | Agent loop | hand it a task and tools, the model plans, calls, observes, repeats | Provider swap | one OpenAIModel line points at OpenAI, Ollama, Bedrock or any endpoint | Observability | stream_async emits every tool call, plus OpenTelemetry traces

[W5D2 s5] AWS Strands: the trade-offs | Advantages, downsides | Any provider | the one-line model swap is cleaner here than almost anywhere else | Lightest loop | a working agent with a tool is three or four lines, no graph wiring | First-class MCP | MCP and A2A built on the official packages, so the idioms transfer | Bedrock default | a bare Agent() expects AWS credentials, so always pass the model | Fast cadence | roughly weekly releases drift the blog posts, so pinning is essential

[W5D2 s7] Pydantic AI: key features | What stands out | MCP | MCPToolset via toolsets=[...], opened with async with agent | Agent loop | one await agent.run() runs the whole tool loop to a final answer | Logfire | two lines instrument every request and tool call, live in the UI | Typed results | pass output_type and result.output comes back validated and typed | Tools | @agent.tool_plain or @agent.tool, schema from hints and docstrings

[W5D2 s8] Pydantic AI: the trade-offs | Advantages, downsides | Type safety | best-in-class typed outputs via a validated result.output | Flexible tools | two decorators, auto schemas, dependency injection via RunContext | Observability | deep zero-config Logfire from the same team, one configure call | No orchestration | no built-in plan or multi-agent primitive, planning is DIY | v1 versus v2 | v2 beta will bring breaking changes, so pin the version or demos drift
